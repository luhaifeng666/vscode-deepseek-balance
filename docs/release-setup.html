vscode-deepseek-balance · 一次性配置

让 GitHub Actions 用身份而非密钥上架

把 Entra ID 身份、Marketplace publisher 和这个仓库串起来，之后每次 git push --tags 就自动发布。总共 11 步，大约 30–40 分钟，全部只需要做一次。

0 / 11 步

为什么要折腾这个？ Azure DevOps 的全局 PAT 将于 2026-12-01 停用，而 Marketplace 发布必须用「All accessible organizations」的全局 PAT —— 没有组织级替代品。所以 OIDC 不是优化，是唯一能活过那个日期的路。

前置条件：一个 Microsoft Entra ID 租户。免费的 Entra 层就够，不需要 Azure 订阅。如果你从没进过 Azure，去 portal.azure.com 注册一个免费账号，它会顺带建好一个默认目录。

建立信任关系

Azure 门户

  1. 在刚建的应用注册里：证书和密码 → 联合凭据 → 添加凭据 → 方案选 GitHub Actions 部署 Azure 资源。

    组织 ID
    9375823
    存储库 ID
    1369352399
    实体类型
    环境（不是分支，也不是标记）
    环境名称
    release
    名称
    github-release

    这两个是 GitHub 的数字 ID，不是用户名和仓库名 —— 门户只要数字。随时可以用这条命令复核：

    gh api repos/luhaifeng666/vscode-deepseek-balance/actions/oidc/customization/sub

    Issuer 和 Audience 会自动填好，不用动：

    Issuer
    https://token.actions.githubusercontent.com
    Audience
    api://AzureADTokenExchange

    保存前确认预览里的 Subject 正好是这一串 —— 这就是双方约定的暗号，一个字符都不能差：

    repo:luhaifeng666@9375823/vscode-deepseek-balance@1369352399:environment:release
    坑

    那两段 @9375823 / @1369352399 不是可选的装饰。GitHub 从 2026-07-15 起对新仓库改用不可变 sub 格式（repo:OWNER@OWNER_ID/REPO@REPO_ID:...），把数字 ID 焊进 subject 里，这样仓库改名或被转让都不会让旧的信任策略意外命中新仓库。本仓库建于 2026-09-14，默认就是新格式 —— 写成不带 ID 的老格式，换 token 会直接失败。

    用环境而不是分支或 tag，则是因为环境名是固定字符串，不需要赌通配符能不能匹配。

阶段 04

取身份的 Resource ID

本地终端

  1. 要拿到 Resource ID，得先以「这个身份的视角」问一句「我是谁」。传统做法是临时建一个 client secret 在本机 az login —— 别这么做，那既要在本机装 Azure CLI，又要凭空造一个长期凭据。

    改成在 GitHub runner 上查：az 预装好了，身份由 azure/login 通过 OIDC 当场换来，一条密码都不经手。临时加一个 .github/workflows/whoami.yml：

    name: 取 resource ID
on:
  workflow_dispatch:
jobs:
  whoami:
    runs-on: ubuntu-latest
    environment: release
    permissions:
      contents: read
      id-token: write          # 换 OIDC token 需要
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          allow-no-subscriptions: true
      - run: |
          az rest -u https://app.vssps.visualstudio.com/_apis/profile/profiles/me \
            --resource 499b84ac-1321-427f-aa17-267ca6975798

    推上去 → Actions → 手动 Run。这一步顺带验证了阶段 03 那条 federated credential 配对 —— 走的 OIDC 路径和正式发布完全一样，subject 写错了现在就会 401。

    坑

    日志里如果出现 ***\efc93ca0-....-.... 这种带星号的 displayName，不是出错。星号是 GitHub 在打码 —— 你的 client ID 或 tenant ID 以字面值出现在输出里，它就会替换成 ***。而这段 GUID 本身是 Azure DevOps 给服务主体自动生成的标识，不会沿用 Entra 里的友好名。身份对不对看的是「az rest 通没通」，不是看这行字。

  2. 返回的 JSON 里那个 "id" 字段就是 Resource ID —— 一串 GUID，跟 client ID / 对象 ID 都不一样。本仓库的值是 eb71e213-0696-62f7-a729-cf533789acf9。

    坑

    499b84ac-1321-427f-aa17-267ca6975798 是 Azure DevOps 这个资源本身的固定 GUID，不是你的任何 ID。别改它。

    如果 az rest 返回 401/403，说明 federated credential 没配对上 —— 最常见的原因是 subject 少写了数字 ID（见阶段 03）。

  3. 它的使命已经完成了，而且它每次都要求 id-token: write。留着就是一条没人看的多余激活路径。

    git rm .github/workflows/whoami.yml
git commit -m "chore: 取到 Resource ID，删掉临时诊断 workflow"

    整套流程从头到尾没有创建过任何长期凭据，这正是走 OIDC 的意义。

阶段 06

配 GitHub

GitHub

  1. 仓库 → Settings → Environments → New environment，名字填 release。

    名字
    release

    workflow 里的 environment: release 就是靠它，让 GitHub 签发的 sub 变成阶段 03 约定的那一串。名字对不上，换 token 就失败。

    顺便可以给它加一条 Required reviewers 保护规则 —— 那样每次发布都要你点一下确认，等于给「误推 tag」上了个保险。

  2. Settings → Secrets and variables → Actions → New repository secret，加两条：

    AZURE_CLIENT_ID
    阶段 02 的应用程序(客户端) ID
    AZURE_TENANT_ID
    阶段 02 的目录(租户) ID
    坑

    是 Secrets 不是 Variables。同一页上两个标签挨着，加错了 workflow 里 secrets.AZURE_CLIENT_ID 会取到空值，报错信息会含糊得多。

阶段 07

发布

本地终端

  1. 10 分钟内不要碰仓库里的文件。第一版还没上架过，所以 0.1.0 直接发就行，不用先升版本。

    git tag v0.1.0
git push origin v0.1.0

    之后每次发布就是三步：改 package.json 的 version、提交、打对应 tag 推上去。tag 和 version 对不上时 workflow 会拦下来。

  2. 仓库 → Actions 标签页，盯着「发布」这一次跑完。成功后用这条确认：

    npx vsce show luhaifeng666.vscode-deepseek-balance

    能打印出版本和描述就说明上架成功了。

    坑

    发布成功但上架页打开是 404，先别慌 —— CDN 传播要几分钟，这不是失败。以 vsce show 的输出为准。

卡住了？按报错对号入座

报错真正的原因
Can not acquire a Microsoft Entra ID access token 换 token 那步挂了。八成是 federated credential 的 subject 对不上：确认它带着 @9375823 和 @1369352399 这两个数字 ID，且 GitHub Environment 确实叫 release。subject 不匹配时错误信息不会告诉你差在哪。
401 / 403 during publish 身份没被加进 publisher 成员，或者角色不是 Contributor；也可能阶段 05 填的是 Entra 对象 ID，而不是阶段 04 查出来的 Resource ID。
AADSTS7000215: Invalid client secret 阶段 04 复制的是「密码 ID」而不是「值」，或者那个密码已经过期/删掉了。重建一个重来。
az rest 返回 401 / 403 当前登录的不是那个 service principal。跑 az account show 看一眼 —— 用自己账号查出来的 profile ID 填进去不报错，但发布会一直 403。
tag vX 与 package.json 里的 Y 不一致 这是 workflow 的保护，不是故障。把版本号同步好再重新打 tag。
上架页 404 CDN 传播，等几分钟。以 vsce show 为准。

如果你今天就想要一个已上架的版本

上面这套是可以等的。想先用旧办法把 0.1.0 发出去，就去 Azure DevOps 建一个 PAT（Organization 选 All accessible organizations，scope 勾 Marketplace → Manage），然后本地 npx vsce publish -p <PAT>。 它能用到 2026-12-01 —— 但全局 PAT 在那天会一起失效，所以这条路只适合「先发出去，之后照样得回来把上面走完」。
